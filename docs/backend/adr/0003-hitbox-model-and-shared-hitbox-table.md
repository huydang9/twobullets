# ADR 0003: Procedural hitbox rig for networked players; `SOLDIER_HITBOXES` moves to `packages/shared`, with a generated rig fit and a drift gate

- Status: Accepted
- Date: 2026-09-14
- Owner: Principal Architect
- Supersedes: [ADR 0206](0206-procedural-capsule-hitboxes.md). Its model is kept; its module placement and verification plan are replaced.
- Related: ADR 0205, ADR 0005; [netcode.md §5.3](../netcode.md#53-hitbox-history-storage), [runtime-performance.md §2.1, §2.3, §6.1](../runtime-performance.md#23-pure-shared-code-shared-codets); `apps/client/src/targets/soldierRig.ts`, `apps/client/src/targets/SoldierHitboxes.ts`, `apps/client/src/combat/HavokRaycaster.ts`

## Context

**The client** (commit 12f0d9c):

- `soldierRig.ts` defines `SOLDIER_HITBOXES`: 13 shapes (head sphere; neck capsule; chest, abdomen and pelvis boxes; 8 limb capsules).
  - Each shape is placed **along a Mixamo bone's +Y axis** in bind-pose metres, scaled by `soldierScale()`.
  - The same file also imports Babylon types (`Node`, `TransformNode`) and client asset types (`CharacterBoneRole`, `CharacterClipName`) for animation.
- `SoldierHitboxes.ts` turns the table into ANIMATED Havok trigger bodies that follow bones after animation. `HavokRaycaster.ts` notes that these are queried as of the last physics step.

**The specialists:**

- **Netcode (ADR 0206):** procedural shapes from replicated pose inputs; the rig lives in `packages/netcode/src/hitreg/rig.ts`; the table should move to `packages/shared`.
- **Runtime:** server skeletal animation would cost only **0.034 ms per tick** for 10 players (runtime-performance.md §2.3). CPU is therefore not a reason to avoid bones. Havok hitbox bodies on the server, however, cost 0.11–0.15 ms per tick (§2.1).

**What decides it:**

- **Rewind:** hit registration rewinds targets by up to 200 ms (ADR 0205). History of pose inputs costs 24 B per player per tick. Bone matrices would cost far more, and animation blend weights depend on render timing, so client and server skeletons diverge anyway.
- **Content hash:** hitbox shapes are gameplay tuning. They change who gets hit, so they belong in the content hash (ADR 0002), next to weapon tables. They don't belong in the network-algorithms package.

## Decision

1. **Model (unchanged from ADR 0206).**
   - Networked players' authoritative hitboxes are posed by a pure function of `{feet, yaw, pitch, stanceBlend}` (later lean, prone, downed, parachute).
   - Hit tests are analytic (ray–sphere, ray–capsule, ray–OBB), with a bounding-capsule broadphase.
   - The static world uses a Havok ray.
   - No Havok bodies for player hitboxes on the server, and none for networked players on the client either.

2. **Where things live.**

   | What | Where | Notes |
   |---|---|---|
   | `SOLDIER_HITBOXES` data, `SoldierHitboxShape`, `SoldierHitboxDef`, and a `HitboxBone` string union (`"head" \| "neck" \| "chest" \| "spine" \| "hips" \| "leftUpperArm" …`) | **`packages/shared/src/hitreg/soldierHitboxes.ts`** | Pure data, no Babylon. Values unchanged; still the **dimensional source of truth**. |
   | `SOLDIER_RIG_FIT`: per stance (stand, crouch), each shape's joint start/end (or centre) in the player's local frame (feet origin, +Z forward) at the canonical aim pose, the shoulder pivot for aim pitch, and the spine pitch share | **`packages/shared/src/hitreg/soldierRigFit.generated.ts`** | Generated by `tools/assets/fit-hitbox-rig.ts` from `swat.glb` (extends `assets:analyze`), committed, reviewed like code |
   | `poseHitboxes(pose, out: Float64Array)`, `boundingCapsule(pose)`, intersectors | **`packages/shared/src/hitreg/{rig,intersect}.ts`** | Allocation-free, `len3` helpers only |
   | Pose history ring, fractional rewind sampling, per-(shooter-D, target, tick) pose cache, segment-vs-rig query | **`packages/netcode/src/hitreg/{history,rewind}.ts`** | Network algorithm, not tuning |
   | Server projectile hit registration | `apps/server-match/src/hitreg/ServerProjectiles.ts` | SoA projectiles (refactor R7) |
   | Client cosmetic hit prediction + `?debug=hitboxes` overlay (procedural shapes drawn over bone-driven ones) | `apps/client/src/net/` + `apps/client/src/debug/` | |

3. **The client keeps bone-driven `SoldierHitboxes`** for offline dummies and the practice range (not networked), and as the visual reference for drift.
   - `apps/client/src/targets/soldierRig.ts` re-exports the table from `@twobullets/shared` and keeps `ACTIONS`, locomotion and `upperBodyWeights`.
   - A type-level check (`satisfies Record<HitboxBone, CharacterBoneRole>`) keeps the bone names aligned.

4. **Drift gate (replaces ADR 0206's manual overlay-only check).** `tools/assets/verify-hitbox-rig.ts` samples the soldier clips `idle` (aim), `walk_*`, `run_*`, `crouch_walk_fwd`, `fire` and `reload` at 10 normalized times. For each shape it compares the bone-driven centre with the procedural centre at the same `{yaw, pitch, stance}`.
   - **Fail CI** if the head or torso centre error exceeds 10 cm in any aim-pose sample, or 15 cm in any locomotion sample.
   - **Warn** at 5 cm.
   - Also report the share of mesh vertices outside all shapes (art constraint from ADR 0206).

5. **Upgrade path (unchanged):** pre-baked per-clip tracks of the table shapes plus replicated blend parameters (+~8 B per player-tick of history). Triggered if hit-reg agreement (architecture.md §6.8) drops below 99% on moving targets, or if playtest complaints cluster on limbs or head during reload or sprint.

## Consequences

- One table drives the client's dummies, the server's authority, the client's cosmetic prediction and the debug overlay. The table and fit change `contentHash`, which forces a matched client and server release.
- `packages/netcode` stays free of gameplay data; `packages/shared` gains a `hitreg` folder.
- The rig fit needs a small asset-pipeline script (M4 task, owned by the client/asset engineer) before server hit registration can be validated.
- Hitboxes won't follow exaggerated animation poses. The drift gate turns that into a measured, reviewable number.

## Alternatives considered

- **Bone-driven hitboxes on the server** (animate 10 skeletons). Affordable in CPU (0.034 ms), but history needs bone matrices and blend weights, and client and server skeletons diverge through frame-timed cross-fades. Rejected.
- **Rig in `packages/netcode` (ADR 0206 as written).** Couples gameplay tuning to a network package and hides it from the content hash. Rejected.
- **Table stays in the client and the server copies it.** Two sources of truth. Rejected.
- **Havok ANIMATED trigger bodies on the server.** 0.11–0.15 ms per tick, a one-step query lag, and no rewind without re-stepping. Rejected.
